Does it leak? — mount, destroy, repeat, and watch what does not come back

This is R6, and R6 is the only row on that list that does not need a Pi, a switch or a physical swap. "Nothing has run for longer than a few minutes. A bedside screen runs for weeks. Object URLs, the scan loop, the wake lock, the settings poll — none of it has been soaked, and the failure mode of a leak is a screen that dies at 3am."

You do not have to wait three weeks to find out that something adds a timer every time it is mounted. A leak is growth per cycle, and growth is measurable in under a minute.

What is measured: outstanding intervals, un-fired timeouts, un-cancelled animation frames, un-revoked object URLs, listeners left on window/document, and DOM nodes. Nothing is read from a source file — the browser's own registries are wrapped and the real modules are run through the real mount/destroy contract. Twice in the previous session a count taken by reading source patterns turned out to be wrong.

A one-time cost is not a leak. A module's first mount legitimately does things it never does again. What a leak looks like is a cost that recurs — so the first two cycles are thrown away and the slope of the rest is what gets reported.
